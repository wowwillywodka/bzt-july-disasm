# Счётчик врагов и статистика июльского BZT

Разбор относится к исходному ROM SHA-256
`8f0af150b642e1e190566a96d19732695164d926244764407560949cee02d8b0`.
Это контракт существующего кода, а не исправление его поведения. Важно
разделять три величины: счётчик игрового HUD, число смертей для экрана
статистики и количество маркеров в картах эпизода.

| RAM | Имя | Писатель → читатель |
|---|---|---|
| `$FF2A74` | `LegacyObjectiveFloor` | при загрузке получает начальный `CurrentFloor`; `CountLegacyObjectiveFloorEnemies` выбирает по нему актёров и смещение сканирования |
| `$FF2A76` | `FloorClearMessageTimer` | нуль разрешает пересчёт; при нулевом результате ставится `$E1`, затем `UpdateStatusMessages` поддерживает цикл сообщений |
| `$FF2A78` | `RemainingEnemyCount` | результат пересчёта 0…99, выводится в HUD |
| `$FF2A7A` | `LastDrawnEnemyCount` | при входе в сцену ставится `$FFFF`; сравнивается перед записью HUD |
| `$FF0E36` | `ObjectiveProgressCount` | попадание в особую клетку `$79` → статистика прогресса |
| `$FF0E38` | `EnemyDeathsRecorded` | 11 обычных путей смерти → экран статистики |
| `$FF0E3E` | `EnemyHitCallbacksRecorded` | допустимые по состоянию hit callbacks → расчёт процента попаданий |
| `$FF0E40` | `EpisodeObjectiveCellTotal` | загрузчик считает клетки типа `$79` в арене → экран статистики |
| `$FF0E42` | `EpisodeEnemyTotalForStats` | загрузчик суммирует выбранные типы и индексы клеток → экран статистики |

## Что именно считает игровой HUD

`CountLegacyObjectiveFloorEnemies` `$0293DE` немедленно выходит при ненулевом
`FloorClearMessageTimer`. В ином случае он:

1. Обходит список до `ActiveActorCount`, учитывая актёра при совпадении младшего
   байта `LegacyObjectiveFloor` с `ActorFloor` и `(ActorFlags & $14)==$14`.
2. Читает **ровно `$400` байт** от `VisibleMapWindow +
   LegacyObjectiveFloor*$400`. Каждый байт преобразует через
   `CellTypeByIndex`. Учитывает типы `$29..$2B` и `$65..$6B`.
3. Ограничивает сумму числом 99, сравнивает её с `LastDrawnEnemyCount`,
   записывает цифры в VRAM при неравенстве и сохраняет сумму в
   `RemainingEnemyCount`.
4. При нуле ставит таймер `$E1` и сообщение `ZeroEnemiesRemaining`.

Это **не** подсчёт всей карты текущего этажа. Видимое окно занимает
`$FFA5FA..$FFA9F9` и содержит 32×32 байта. Уже при `LegacyObjectiveFloor=1`
сканирование начинается с `$FFA9FA`, за окном: далее находятся область
анимаций текстур и, начиная с `$FFB9FC`, упакованные карты всех этажей.
Обычный переход между этажами меняет `CurrentFloor` и окно, но не обновляет
`LegacyObjectiveFloor`. Даже при нулевом значении этого поля подсчёт охватывает
только видимое окно, которое движется за игроком.

Статическая проверка исходных карт показывает масштаб расхождения ещё до
создания актёров и изменения клеток. «Окно» ниже — 32×32 при **первой**
стартовой клетке `$77`; это не предсказание реального HUD после спавна.

| Эпизод, этаж 0 | Маркеров указанных типов во всей карте | В стартовом окне |
|---|---:|---:|
| 1 | 34 | 17 |
| 2 | 73 | 27 |
| 3 | 73 | 51 |
| 4 | 0 | 0 |

Последняя строка показывает лишь отсутствие **этих старых типов** в карте;
живые актёры и иные типы врагов учитываются отдельно либо вовсе не входят в
формулу. Расчёт всех 33 исходных карт воспроизводится командой
`python3 tools/audit_enemy_count.py --write`; подробности сохраняются в
`metadata/enemy_count_audit.json` исследовательской копии.

## Когда счётчик перестаёт обновляться

`RunGameplayIteration` `$00144E..$00145E` вызывает пересчёт при нулевом
таймере и `GameTick & $3F == 0`. Некоторые смерти, спавны и переход этажа
вызывают его непосредственно, но всё равно проходят начальную проверку
таймера. После результата 0 таймер становится `$E1`. В
`UpdateStatusMessages` `$020AEA..$020B18` он отсчитывается до `$69` с
сообщением `ProceedToNextLevel`, затем до нуля с сообщением `FloorSecured`,
после чего **снова ставится `$E1`**. Пока нет явного сброса при загрузке сцены
или формировании прогресса, последующие вызовы подсчёта ничего не меняют,
даже если враг появится вновь или игрок сменит этаж.

Кэш HUD тоже не работает как кэш: среди прямых обращений к
`LastDrawnEnemyCount` есть только инициализация `$FFFF` в `$001052` и
сравнение в `$029466`. `WriteTwoDigitHudNumberToVram` меняет лишь VRAM,
не это слово. Поэтому каждый состоявшийся пересчёт числа 0…99 повторно
записывает две цифры. При возврате из паузы `InitializeGameplayVideo`
перерисовывает ранее сохранённый `RemainingEnemyCount`, не пересчитывая карту.

`FloorNotSecured` на переходных клетках (`$00F09A/$00F0FA/$00F15A`) —
сообщение по таймеру и начальному этажу, **не запрет** движения лифта.
`SceneExitRequested` счётчиком врагов не устанавливается. Эти пути нельзя
соединять в предполагаемое правило «всех убил → автоматически прошёл этаж».

## Статистика — другая система

`LoadEpisodeGeometry` `$0973CA..$0974AE` считает в фиксированной арене
`EpisodeMapCells` `$4000` байт, а не на выбранном этаже. Для
`EpisodeEnemyTotalForStats` он суммирует типы `$29..$2C`, `$65..$6B`,
`$08..$0A`, `$27` и удвоенное количество индексов `$EC..$EF/$F4..$F7`.
Загрузчик не очищает хвост арены после уложенных сеток, поэтому значение
потенциально включает старые байты хвоста. Экран статистики сопоставляет
этот общий знаменатель с `EnemyDeathsRecorded`; он не должен подменять
`RemainingEnemyCount` для текущего этажа.

`EnemyDeathsRecorded` увеличивают 11 обычных входов смерти. Ветка
`EnterLegacyEnemyDeathEffect` при ненулевом `ActorAlternateDeathSignal`
обходит эти инкременты; обычный ненулевой производитель сигнала пока не
установлен. `EnemyHitCallbacksRecorded` увеличивается после проверки
состояния, но **до** отбрасывания попадания по дальности/урону. У Denpyder
пробуждение из состояния 7 также увеличивает его без потери HP.
Статистика точности берёт `(EnemyHitCallbacksRecorded*100) /
(AmmoUsageFixedCounter>>8)` при ненулевом знаменателе.

При переходе к следующему эпизоду `HandleSceneExit` обнуляет прогресс
клеток, записанные смерти и расход боеприпасов, но не
`EnemyHitCallbacksRecorded`; прямого сброса последнего между эпизодами
не найдено. Это ещё одно несоответствие для будущего исправления статистики.

Для ромхака сначала нужно определить целевую семантику «оставшихся врагов»:
все маркеры **текущего этажа** в packed-карте плюс уже созданные живые актёры,
с исключением трупов и предотвращением двойного счёта. Затем отдельно
решить, как учитывать неуспешное выделение актёра, выход актёра за окно,
сетевых актёров и новые виды врагов. Существующий код такой контракт не
реализует; здесь он сохранён побайтово.
